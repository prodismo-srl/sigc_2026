Procedimiento de Separación de Entornos de Desarrollo

Código: P522-IT-1
Última revisión: 18/11/2026
Rev. N°: 2
Cumple: TISAX (VDA ISA 5.2.2), ISO 27001:2022 (A.8.31)

1 OBJETIVO

Describir los pasos para evaluar la necesidad de separar entornos, mantener la separación de los entornos de SIP4.0, gestionar los accesos de personas y proveedores y pasar cambios a producción, según la MC522-IT-1 y el control 5.2.2 de TISAX.

2 EVALUACIÓN DE RIESGOS

Paso Responsable Registro
1. Identificar los sistemas con desarrollo o pruebas (propios o de proveedores) y los datos que contienen, con su clasificación (MC132-IT-1) RSI M522-IT-2
2. Evaluar el riesgo de desarrollar o probar sin separación (Bajo, Medio, Alto) y decidir: entornos separados, pruebas en el entorno del proveedor, o pruebas sobre copias o con piloto RSI M522-IT-2
3. Definir los requisitos del entorno (infraestructura, datos, herramientas, credenciales, usuarios) y verificar que se cumplen RSI / desarrollador M522-IT-2 (estado y verificación)
4. Repetir la evaluación ante un sistema o desarrollo nuevo, un cambio de proveedor o de infraestructura, y en la revisión semestral (V-39) RSI M522-IT-2 (nueva revisión)

3 ENTORNOS DE SIP4.0

Aspecto Desarrollo Pruebas (staging) Producción
Infraestructura Máquina virtual propia en Azure, con IP y URL propias Máquina virtual propia en Azure (staging.sip4.prodismo.com) Máquina virtual propia en Azure (sip4.prodismo.com)
Base de datos PostgreSQL propia PostgreSQL propia PostgreSQL propia

Herramientas Herramientas de desarrollo permitidas Lo necesario para probar Solo lo necesario para que el sistema funcione: sin IDE, compiladores, Git ni clientes de base de datos de escritura
Credenciales Propias del entorno Propias del entorno (distintas de producción) Propias del entorno (distintas de desarrollo y pruebas)
Usuarios Desarrollador Desarrollador y usuarios clave con usuarios de prueba, distintos de los de producción Usuarios de negocio con permisos por grupo (MC421-IT-1); administradores: Germán Montalbetti y Nicolás Donato

Verificación de la separación

  1. Las tres máquinas virtuales y las tres bases de datos PostgreSQL son distintas (IP, URL y credenciales).
  2. En el servidor de producción solo está instalado el software necesario para funcionar; se revisa la lista de programas instalados.
  3. Las bases de desarrollo y staging contienen solo datos de prueba.
  4. Los usuarios clave tienen usuarios de prueba en staging.
  5. El resultado se registra en el F151-IT-5 (V-39) y, si algo no se cumple, en el F151-IT-4.

4 ACCESOS A LOS ENTORNOS

Paso Responsable Registro
1. Pedir el acceso al entorno indicando persona o proveedor, entorno, nivel (usuario, base de datos, servidor, administrador) y motivo Responsable del área / IT F412-IT-1
2. Aprobar; los accesos a producción con privilegios los aprueba el RSI RSI F412-IT-1
3. Crear la cuenta propia del entorno (sin reutilizar credenciales de otro entorno) y registrarla IT / desarrollador M522-IT-1 · F421-IT-2 (cuentas privilegiadas)
4. Quitar el acceso cuando ya no se necesita y cambiar las credenciales compartidas que la persona o el proveedor conocía IT M522-IT-1 · F521-IT-2

Accesos de proveedores

  • Enter-Geminus: el 1/12/2026 se quitan sus accesos a Azure, a las máquinas virtuales, a las bases de datos, a SIP4.0 y a GitHub, y se cambian las contraseñas que conocía. Se registra en el F521-IT-2 y en la M522-IT-1.
  • Cubits SRL (App de Viajes): para un despliegue en producción, el IT Manager habilita la IP que informa el proveedor en el servidor de Donweb, supervisa el despliegue, quita la IP al terminar y registra el cambio en el F521-IT-2.
  • Otros proveedores (por ejemplo, Kolossus): sesión remota por AnyDesk iniciada y supervisada por el IT Manager, solo para el trabajo pedido.

5 PASE A PRODUCCIÓN DE SIP4.0

Paso Responsable Registro
1. Desarrollar en el entorno de desarrollo y subir el código a una rama de GitHub Desarrollador GitHub
2. Abrir un pull request y desplegar la versión en staging Desarrollador GitHub (pull request)
3. Probar en staging con usuarios clave y usuarios de prueba; registrar el resultado Usuarios clave / desarrollador F521-IT-2 (pruebas)
4. Aprobar el pull request y el pase a producción Germán Montalbetti GitHub · F521-IT-2
5. Hacer una copia de seguridad de la base de datos de producción Quien despliega F521-IT-2 (respaldo)
6. Desplegar en producción (hasta el 30/11/2026, Enter-Geminus; desde el 1/12/2026, Nicolás Donato) Quien despliega F521-IT-2
7. Verificar el funcionamiento y los requisitos de seguridad (permisos, HTTPS) y cerrar el registro Desarrollador / RSI F521-IT-2

No se modifica código ni datos directamente en producción. Si un incidente lo exige, lo autoriza el RSI y se registra en el F521-IT-2 como cambio de emergencia, con la consulta o corrección ejecutada.

6 DESPLIEGUES DE LA APP DE VIAJES

  1. Cubits SRL desarrolla y prueba en su entorno de pruebas, con datos de prueba.
  2. Cubits pide el despliegue por correo; el IT Manager lo aprueba y acuerda la ventana.
  3. El IT Manager habilita la IP del proveedor en Donweb, supervisa el despliegue y quita la IP al terminar.
  4. Se verifica el funcionamiento (inicio de sesión, HTTPS, datos personales protegidos) y se registra en el F521-IT-2.

7 AUTOMATIZACIONES MENORES

  • Power Apps: desarrollar y probar con una copia de la lista o del origen de datos, o con datos de prueba; publicar después de probar. El historial de versiones permite volver atrás.
  • Macros de Excel o CATIA: probar sobre una copia del archivo, no sobre el original.
  • Si la automatización usa información confidencial o afecta a varias áreas, registrar el cambio en el F521-IT-2.

8 DATOS DE PRUEBA

  • Los entornos de desarrollo y staging se cargan con datos ficticios o de prueba.
  • No se copian bases de producción a desarrollo o staging. Si fuera imprescindible, se anonimizan antes, lo aprueba el RSI por escrito y se registra en el F521-IT-2.
  • Los proveedores no usan datos reales de PRODISMO en sus entornos de pruebas.
